明星项目拆解——AgentCube、Agent Sandbox、KAI Scheduler、Volcano如何接住Agent

发表于 2026-09-07 分类于 洞察
本文字数： 2.2k 阅读时长 ≈ 2 分钟

💡 一句话总结：四个K8s生态明星项目，各自修好了AI基础设施的一处错位——本文逐个拆解它们原来治什么病、动了什么手术、效果差多少。

上篇回顾：三个错位

上一篇《4970亿美元买来了什么——AI基础设施的三个错位》讲了一个判断：AI基础设施不缺钱不缺卡，缺的是调度与隔离能力。

👉 上篇传送门

那篇文章留下了三个错位：利用率错配（GPU平均利用率仅5%）、进程重定义（K8s为旧进程设计，Agent是新物种）、战场打错（延迟瓶颈在CPU不在芯片）。

这篇文章不谈观点，谈药方。四个明星项目，正好对着错位开药：AgentCube和Agent Sandbox解”进程重定义”，KAI Scheduler解”利用率错配”，Volcano解决gang调度的死锁问题。

用开餐馆打个比方，这四个项目分别管：包间怎么留、包间结不结实、桌位怎么排、客人怎么一起进门。

🍱 AgentCube：客人走了，包间别拆

原来的毛病：K8s的Pod（容器组）一旦缩容或空闲，直接删除，内存状态全部蒸发。Agent的对话上下文、加载的模型就住在内存里，删一次就得重来。重建一次要秒级，用户盯着”转圈加载”干着急。

动了什么手术：AgentCube引入Pod暂停机制。Pod不再被删除，而是像酒店”锁门保装修”——客人退房，家具、装修全留着，只清走活动物品。下次同一客人回来，直接开门入住。

效果：会话恢复从秒级降到几十毫秒，快了两个数量级。用户体感从”转圈加载”变成”秒回”。对Agent这种几分钟到几小时的长会话，这个差距就是体验的分水岭。

🏦 Agent Sandbox：从纸板隔断到银行金库

原来的毛病：普通容器之间共享操作系统内核，隔断像纸板糊的。AI生成的代码要真实执行，万一它来一句rm -rf /呢？共享内核的容器根本挡不住。”信任但验证”的传统思路，对会自己写代码的Agent彻底失效。

动了什么手术：GKE Agent Sandbox换成gVisor和Kata这类强隔离方案——相当于把纸板隔断改成银行金库，Agent的每一个系统调用（程序请求操作系统做事的动作）都被金库管理员逐个拦截检查。原则只有一个：永远不信任，永远验证。

效果：沙箱创建每秒可达300个，延迟小于1秒，成本还低30%。快照恢复能做到毫秒级”开门”。隔离强度和创建速度第一次同时达标。

🔪 KAI Scheduler：整卡出租改按份切

原来的毛病：K8s默认把一整张GPU租给一个任务。而很多推理任务只吃几GB显存，整卡大部分算力在空转。这就是上篇说的利用率5%的病根之一——不是没活干，是桌子太大不敢拼桌。

动了什么手术：KAI Scheduler支持GPU分片调度，把一张卡切成多份，显存之间硬隔离（彼此看不见、抢不走）。一个任务占用多大切多大。

效果：一张卡从只跑1个任务，变成同时服务5到10个任务。GPU利用率从个位数提到70%以上。同样一批卡，产出翻了几倍。

🚪 Volcano：凑齐再进

原来的毛病：分布式训练像团餐，必须整桌人到齐才开席。K8s默认调度是来一个安排一个——结果99张卡已分配、还差1张卡被别人占着，这99张卡就集体干等。资源死锁，谁也动不了。

动了什么手术：Volcano引入Gang调度（成组调度）：一桌8个位子，要么8个位子一次全留出来，要么一个都不留。”凑齐再进”，绝不放半桌客人进去干瞪眼。

效果：部分分配导致的资源死锁被从机制上杜绝。大模型训练动辄几千卡，没有Gang调度根本排不开队——这也是它成为K8s批调度事实标准的原因。

🧩 还有两块拼图

同谱系里还有两个项目值得点名。Kueue管队列配额：算力不够时任务排队等位，而不是一起挤进去互相踩踏——它是利用率错配的”排队叫号系统”。Fluid管数据缓存：把训练数据提前搬到离GPU近的地方，治的是”Agent在等什么”里的等I/O那一半。

这两个是配角，但思路一致：先承认资源稀缺，再设计排队和搬运的规矩。

💭 原创观点：这批项目的共同哲学是什么

拆完四个项目，回头看它们共享一个底层转向。

从管理机器，到服务会话。 K8s管的对象是”机器上的进程”：短命、无状态、随时可杀。这四个项目管的对象是”会话”：长命、有状态、必须留装修。AgentCube留装修，Sandbox验证每个动作，都是在服务一个会话的完整生命周期。

从信任边界，到不信任边界。 旧世界的容器假设里面跑的是自家微服务，纸板隔断够用。新世界的容器里面跑的是AI生成的任意代码，金库是唯一选项。信任模型换了，隔离架构就得跟着换。

所以我不同意”K8s失败了”的说法。更准确的说法是：K8s没有死，是Pod的概念死了一半。 Pod还在，调度器还在，但”可随意删除、默认信任”的那一半假设已经死了，新长出来的那一半，就是这批明星项目。

上篇说错位孕育机会，这篇给出证据：机会不在发明新系统，而在沿着错位的裂缝，把旧地基重新浇筑一遍。

✅ 总结

  1. AgentCube和Agent Sandbox解决”进程重定义”：会话要保得住（暂停恢复毫秒级），代码要防得住（系统调用全拦截）。
  2. KAI Scheduler和Volcano解决”利用率错配”：切卡把利用率从5%提到70%+，Gang调度杜绝整队干等。
  3. 共同哲学：从管理机器到服务会话，从信任边界到不信任边界——K8s没有死，是Pod的概念死了一半。
