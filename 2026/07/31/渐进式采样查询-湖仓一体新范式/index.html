渐进式采样查询——突破湖仓一体的新范式

发表于 2026-07-31 更新于 2026-08-02 分类于 学习
本文字数： 7.4k 阅读时长 ≈ 7 分钟

📝 AI 摘要

传统数据库追求精确扫描全量数据，这在PB时代不可持续。渐进式采样查询范式将”模糊优先、精确按需”作为默认行为——聚合查询默认走采样获得毫秒级近似结果，详情查询先采样定位再精确获取，通过表格式内建采样能力实现用户无感上车，最终统一湖仓三层数据源。

💡 一句话总结：未来数据库的默认行为不应该是”扫描所有数据给精确答案”，而应该是”先采样给模糊答案，再按需精确”——这像渐进式图片加载一样，先模糊后清晰，让用户在毫秒内获得方向性判断，再决定是否值得等待精确结果。

核心问题：为什么精确优先的范式已经走到尽头

传统范式的致命假设

传统数据库有一个隐含假设：用户需要精确答案，系统必须扫描全量数据。

这个假设在数据量小的时候没问题。但当数据量从GB到TB到PB时，这个假设变成了诅咒：

数据量 全表扫描延迟 用户真正需要
1GB 100ms 精确答案
100GB 10秒 可能精确，可能近似就够
10TB 17分钟 99%的场景近似就够
1PB 28小时 绝大多数分析只要近似

现实是：绝大多数分析查询不需要精确答案。

业务方问”上个月GMV是多少”，他要的是”大概3亿还是5亿”的方向性判断，不是”324,782,191.37”的精确数字。但传统数据库为了给出精确数字，要扫描几十GB数据，等待几十秒。

缓存、物化视图、预聚合为什么不够

方案 问题
缓存 命中率天花板、数据新鲜度问题、缓存失效成本
物化视图 预定义维度有限、无法覆盖即席查询、维护成本高
预聚合 丢失细节、维度爆炸、只能回答预设问题
Cube/OLAP 建模重、维度组合爆炸、对新数据源适应性差

这些方案都是”提前算好”的思路——预计算所有可能答案。但即席查询的组合是无限的，预计算永远追不上需求。

需要一种新的范式：不预计算答案，而是减少计算量。

新范式：渐进式采样查询（Progressive Sampling Query）

核心理念

借鉴渐进式图片加载（Progressive Image Loading）：

用户在50毫秒内就能看到”大概3亿”，然后自己决定是否等2秒看”3.05亿”，还是直接用3亿做决策。

明细查询的采样范式

用户说”我要看华东地区的大额订单”——这本质上是明细查询，传统方式要扫描全表过滤。新范式：

关键洞察：采样不是替代精确查询，而是帮助用户快速缩小精确查询的范围。 这就是”指数下降后再精确获取”的精髓——采样让搜索空间从1亿行指数级缩小到几千行，然后精确查询成本就微不足道了。

技术实现：表格式内建采样

Iceberg表格式扩展

采样不应该是外挂式的，而应该内建到表格式中——让采样成为表的一等公民。Iceberg 的 SamplingSpec 属性应维护多级采样（0.1%/1%/5%/10%），每级记录采样率、方法、采样子集文件与统计信息。

采样方法分五类：系统采样（按文件块随机）、伯努利（按行）、分层（按分组列）、蓄水池（流式）、索引采样（基于索引列）。

自描述采样（Self-Describing Sampling）

表格式 manifest 自带采样元数据：每个采样级别记录采样率、采样子集文件列表、行数、置信度、刷新策略。任何支持 Iceberg 的引擎（Trino、Spark、Flink、DuckDB）都能透明读取采样数据，零额外配置。

增量采样维护

数据写入时触发增量采样：1% 池每 100 行取 1 行，5% 池每 20 行取 1 行，10% 池每 10 行取 1 行——采样数据与主数据秒级同步。

关键：不是维护独立的采样表，而是通过文件级别的元数据标记实现——主数据文件中哪些 block 属于哪个采样级别，查询时直接选择对应 block 读取。

Zone Maps + 采样的协同

采样和 Zone Maps 是天然互补的：Zone Maps 过滤后剩余 10% 文件，再 1% 采样后实际扫描全表的 0.01%——Zone Maps 减少 90%，采样再减少 99%，总体减少 99.9% 的 I/O。

这就是”让大数据变成小数据”的数学证明——Zone Maps 减少一个数量级，采样再减少两个数量级，三次叠加后 1PB 数据变成 1GB 扫描量。

大一统：湖仓一体的破局点

当前数据架构的三难困境

当前三类方案各自为政、互不兼容、查询体验割裂：HTAP（事务分析一体）、湖仓一体（结构化+半结构化统一）、数据湖联邦（多源跨平台统一）。用户要跨 TP 数据库、数据湖、外部数据源做分析，传统方案要么联邦查询（Trino/Presto 能跨源但全量扫描慢）、要么数据搬运（ETL 延迟大成本高）、要么数据共享（Iceberg/Delta 只解决湖内共享，不解决 TP 和湖之间的鸿沟）。

采样范式为什么能统一三层

因为采样归一化了不同数据源的查询速度：

数据源 全量扫描 1%采样扫描 速度差异
TP行存（NVMe） 10秒 0.1秒 100x
AP列存（SSD） 30秒 0.3秒 100x
数据湖（S3/OSS） 5分钟 3秒 100x
外部JDBC（MySQL） 10分钟 6秒 100x

全量扫描时，TP和S3的速度差30倍——用户体验割裂。但1%采样后，TP是0.1秒，S3是3秒——都在”可接受”范围内，用户体验统一。

统一查询接口

用户写一条标准 SQL 透明跨源：SELECT o.region, SUM(o.amount) ... FROM mysql.orders o JOIN lake.user_profile u ON ... JOIN ext_crm.customer_tags c ON ...——TP 行存（热）、数据湖 Iceberg（温）、外部 JDBC（冷）三源 JOIN，系统内部走三阶段渐进采样。

系统内部三阶段执行：阶段一全局采样（50ms-3s，各源 1% 采样 + 采样集上 JOIN），阶段二扩大到 5% 采样降误差到 ±1.5%，阶段三按需全量 JOIN。

关键：联邦查询的瓶颈永远是最慢的数据源。 全量扫描时 S3/JDBC 拖慢整体；采样后各源速度差缩小，联邦查询变得可行。

外部数据目录兼容

采样范式的另一个优势——外部数据源不需要改表格式就能受益：

数据源类型 采样实现方式 用户感知
Iceberg原生表 内建采样元数据，零开销 最优体验
Parquet/ORC文件 文件级系统采样（随机选文件） 接近最优
Hive表 文件级采样 + Hive统计信息辅助 良好
JDBC数据源 TABLESAMPLE透传或应用层采样 可用
API/REST数据源 应用层采样 + 缓存 基本可用

Iceberg原生表格式数据达到最优——因为采样元数据内建在表中，引擎可以直接定位采样文件，零额外开销。外部数据源通过适配层实现采样，性能稍逊但仍然可用。

采样质量控制

误差保证

不是随机采样就完事——必须给出统计保证。基于置信区间公式（点估计 ± Z × σ/√n，Z=1.96 对应 95% 置信度），1% 采样 100 万行得到 1 万样本时，SUM 聚合误差通常 < 0.001%。

系统自动计算并返回精度元数据：结果值、置信度、各分组误差范围、采样量、执行耗时、全量扫描预估耗时、是否可提升精度。

自适应采样率

不同查询需要不同采样率——系统自动选择：误差容忍 5% 用 1% 采样（快），1% 用 5% 采样（中速），0.1% 用 20% 采样（较慢），精确则全量扫描。决策因素包括数据分布方差、查询复杂度（JOIN 需双侧采样）、用户误差容忍度、时间预算。

分层采样处理数据倾斜

数据不均匀时简单随机采样效果差——小分组可能样本极少导致误差爆炸。分层采样按分组列分层后各层独立采样，并对小分组保底至少 100 行，保证各层误差均匀。

用户无感上车策略

为什么”无感”是成功的关键

技术再好，如果要求用户改SQL、改应用、学新语法——大概率推不动。采样范式要成功，必须零改动上车。

四层无感设计

第一层：SQL 零改动 — 用户写标准 SQL，引擎内部自动改写为 TABLESAMPLE(1%) 并对聚合结果乘以采样倍率。

第二层：结果自动标注 — 返回结果自动附带精度信息（如”华东 ≈2.8亿 ±5% (1%采样)”），但不打断使用流程，附带”提升精度/导出/可视化”操作入口。

第三层：BI 工具适配 — Tableau/Superset/Metabase 通过标准 JDBC 连接，采样结果自动呈现。JDBC 驱动在返回结果的同时返回精度元数据，BI 工具无需适配。

第四层：表格式自描述 — Iceberg 表创建时自动启用采样，不需要 DBA 配置。数据写入时自动维护多级采样、Zone Maps、采样统计信息，查询时自动使用。

渐进式上车路径

四阶段推进：阶段一引擎层自动采样（升级 Trino/StarRocks/Calcite 即可获得 2-10 倍加速，零改动）；阶段二 Iceberg 采样元数据增强（新建表自动内建，旧表 ALTER 升级）；阶段三生态集成（JDBC 暴露精度元数据、BI 展示置信区间、应用层渐进式 UI）；阶段四 AI 驱动（预测最佳采样率、自动分层策略、查询模式学习）。

对比分析：为什么采样范式最可能成功

vs 现有方案

方案 核心思路 通用性 上手成本 外部数据兼容 误差可控
缓存 重用历史结果 低（只对重复查询） 中 不兼容 无误差但数据旧

成功的四个必要条件

  1. 零改动上车 — 不需要改SQL、改表结构、改应用代码 → ✓ 表格式自描述 + 引擎自动改写
  2. 误差可控 — 用户知道结果的可靠程度 → ✓ 置信区间 + 自适应采样率
  3. 全场景覆盖 — 聚合/明细/JOIN都受益 → ✓ 分层采样 + 双侧JOIN采样
  4. 跨源统一 — 湖仓一体兼容 → ✓ 采样归一化不同数据源速度

与现有技术的融合点

采样范式不是推翻现有技术，而是在其上增加一层：渐进式采样查询层（意图识别→采样路由→误差估算→渐进精化）叠加在已有的查询优化器（Calcite/Trino/StarRocks）、执行引擎（向量化/MPP/JIT）、表格式层（Iceberg+采样元数据/Parquet+文件采样）、存储层（行存/列存/对象存储）之上。

每一层都保留已有技术，采样层是新增的。Calcite 可扩展为采样感知优化器，Trino 可增加采样路由器，Iceberg 可扩展采样元数据，向量化执行照常工作只是处理的数据量少了 99%。

技术挑战与解法

挑战一：JOIN场景的采样

JOIN 是最难采样的——两表各自采样 1%，JOIN 结果可能只有 0.01% 的行，误差爆炸。

三种解法：大表采样 + 小表全量（orders 1% + users 全量，误差可控）；基于 JOIN 键的分层采样（两表按相同键分层，保证 JOIN 完整性）；图采样（将多表 JOIN 建模为图，随机游走采样保证代表性）。

挑战二：COUNT DISTINCT

COUNT(DISTINCT user_id) 对采样极其敏感——去重计数无法简单按采样率线性放大。

解法：HyperLogLog + 采样。HLL 只需固定内存（通常 16KB），1% 采样 100 万行用 HLL 估算误差约 5%，80ms 返回——对比全量扫描去重 28 秒。

挑战三：数据分布变化

数据分布突变（如某天突然多了 10 倍数据）会让旧采样统计失准。

解法：自适应采样校准——写入时监控分布变化，超阈值触发采样池重建；查询时与 Zone Map 统计交叉对比，偏差大则自动升级采样率。

挑战四：用户信任

用户可能不信任”模糊”结果——尤其是中国企业数据文化偏向精确。

解法：渐进式信任建立——第一阶段采样与精确并行展示让用户看到误差通常 < 5%；第二阶段采样默认展示、精确可选；第三阶段采样成为默认范式，精确查询只用于财务对账等场景。

常见问题

Q: 采样查询会不会给出错误答案？

采样查询提供的是近似结果，不是错误结果。关键是置信区间可控——0.1% 采样在大多数聚合查询上误差不超过 5%。渐进式范式的精髓是”先给模糊方向，再按需精确”，用户根据近似结果决定是否值得等待全量扫描。

Q: 为什么不直接用缓存或物化视图？

缓存和物化视图是”预计算”思路——提前算好结果存起来。问题是：查询组合爆炸、维度变更失效、新鲜数据查不到。渐进式采样是”算得快但模糊”思路——不预存任何结果，对所有查询即时响应，靠采样量控制精度和速度的平衡。

Q: 渐进式采样查询需要改用户的 SQL 吗？

不需要。理想方案是表格式内建采样能力，引擎在执行层自动插入采样算子。用户写普通 SQL，引擎根据查询类型（聚合 vs 详情）自动决定采样策略。这是”用户无感上车”的关键设计。

Q: 采样查询适合所有场景吗？

不适合。需要精确结果的场景（金融对账、合规审计、计数查询）仍然需要全量扫描。渐进式采样适合探索性分析、趋势判断、仪表盘、A/B 实验方向性判断——这些场景占分析查询的 80% 以上。

✅ 总结

渐进式采样查询范式的核心命题：

传统范式：扫描全量数据 → 给精确答案 → 慢但准
新范式：扫描采样数据 → 给近似答案 → 快且够准 → 按需精确

这个范式能统一湖仓一体的根本原因：

  1. 速度归一化 — 采样让不同数据源的查询速度差异从30倍降到3倍，用户体验统一
  2. 零改动上车 — 表格式自描述采样，SQL不需要改，用户无感
  3. 误差可控 — 置信区间让用户知道结果的可靠程度，不是盲目的模糊
  4. 渐进精化 — 先模糊后精确，搜索空间指数级缩小后再全量扫描
  5. 全场景覆盖 — 聚合走采样、明细先采样定位、JOIN用相关性采样、点查走索引

为什么这是最可能成功的技术路线？

因为它满足了成功的四个必要条件——零改动、误差可控、全场景、跨源统一。而缓存、物化视图、Cube等方案都在这四个条件中有短板。采样范式不是替代现有技术，而是在其上增加一个”智能降速”层，让所有现有引擎和表格式都能受益。

最终愿景：让”大数据”在查询时自动变成”小数据”——不是靠缓存，不是靠预计算，而是靠统计学的力量。100倍数据量只需要扫描1%，这就是采样的数学之美。
