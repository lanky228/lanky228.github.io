读书笔记 异常处理的设计与重构

发表于 2020-04-05 更新于 2026-08-22 分类于 学习
本文字数： 3k 阅读时长 ≈ 3 分钟

💡 异常处理的本质不是”捕获错误”，而是”在错误发生时保持系统可控”。catch了不等于处理了，消除错误状态才是处理。

背景：一次线上事故

读这本书的契机，是一次线上P0事故。

当时我们有个支付接口，调用的下游服务超时了。代码里catch了超时异常，记了日志，然后返回了一个默认值。看起来没问题——直到发现这个”默认值”被后续流程当作正常结果处理，导致一批用户的订单状态错乱。

排查时发现：catch了异常，但没有恢复状态；记了日志，但没有阻断错误传播。异常被”处理”了，系统却不可控了。

这就是大多数开发者对异常处理的认知盲区——以为catch了就是处理了。这本书让我意识到，异常处理是系统设计问题，不是语法问题。

四个概念别混着用

很多人混用”错误”和”异常”，但它们是不同的东西：

  • Fault（缺陷）：代码写错了。空指针、逻辑错误。这是根因。
  • Error（错误）：缺陷导致系统进入错误状态。比如接口内部出错。
  • Failure（失败）：错误状态传播到外部，用户可见的功能丧失。比如页面白屏。
  • Exception（异常）：编程语言中传递上述信息的对象机制。

缺陷→错误→失败，是一条传播链。

我那个支付事故就是典型的：下游超时（Fault导致的Error）→ catch后返回默认值（Error没消除）→ 订单状态错乱（Failure）。

异常处理的目标是在传播链的每一环截断它。我的代码在第一环就失败了——catch了异常但没消除错误状态。

最被忽视的原则：不要返回null

这本书里让我触动最深的一条：返回null是bug的温床。

每个调用方都必须记得检查null，但总有人忘。而且null的语义模糊——是”没有数据”还是”出错了”还是”未初始化”？

更好的做法：

  • 返回空字符串""代替null字符串
  • 返回空List代替null集合
  • 使用Null Object模式（返回一个行为正确的空对象）

null逼调用方写防御代码，空对象让调用方无感知。

这不是技巧，是设计哲学。我后来在团队里推了一条规范：禁止方法返回null，必须用Optional或空集合替代。推行三个月后，NPE类bug减少了约70%。

异常处理的四个等级

书里把异常处理能力分成四级，这个框架特别实用：

等级0：未定义

系统没有异常意识。HTTP 200，return code 0，但功能是否正常不确定。出了问题也不知道。

等级1：错误报告

接口失败时返回具体错误码。至少告诉你”出了什么错”。

规则：不忽略已查异常；不捕获未查异常（Runtime异常说明代码有bug，该修不该catch）；转抛异常时不记日志（日志在最外层记）；最外层捕获所有异常。

等级2：状态恢复

不仅报告错误，还恢复系统状态。包括向后恢复（撤销操作、恢复原数据）和内存清理、资源释放。

等级3：行为恢复

异常时执行备用逻辑，系统继续工作。包括诊断、隔离、重新配置、重试、向前恢复（使用备用数据继续处理）。

等级越高，系统越健壮。但大多数项目停在等级1——只报告不恢复。

我的支付事故就是典型的等级1：catch了异常，记了日志，返回默认值。如果做到等级2，应该在catch后回滚事务状态。如果做到等级3，应该重试或走降级逻辑。

我在实际项目中的应用

读完这本书后，在团队里推了几项实践：

第一，异常处理策略文档化。每个核心接口明确标注：哪些异常预期会发生、各自走什么恢复策略。不再是”catch了再说”，而是先设计后编码。

第二，分层异常处理。DAO层抛基础设施异常（SQLException），Service层包装成业务异常（PaymentFailedException），Controller层统一兜底转HTTP响应。每层只处理自己层的关注点。

第三，消除null返回。全局搜索所有return null，逐一替换为Optional或空集合。改动量大，但收益最明显——NPE类事故几乎消失。

第四，finally只做资源释放。之前有人在finally里写业务逻辑（比如状态更新），一旦try块异常，finally里的逻辑可能基于错误状态执行，造成二次问题。改成只做资源释放后，这类问题消失了。

资源管理的陷阱

finally会吞掉异常

如果try块抛出异常A，finally块又抛出异常B，最终抛出的是B——A被吞掉了。

这是Java异常处理的经典陷阱。解决方案：try-with-resources（Java 7+）。它自动关闭资源，且不会丢失try块的异常。

try/catch/finally的职责

  • try：资源初始化 + 逻辑处理。只放可能抛异常的代码。
  • catch：异常处理 + 流程重试。捕获你预期会发生的异常。
  • finally：只做资源释放。不要放业务逻辑。

这三个块的职责混淆是代码坏味道的重灾区。

异常设计的原则

命名要表达内容

NotFoundException比Exception12好一万倍。异常名本身就是文档。

低级异常转高级异常

底层抛出的SQLException应该被包装成UserNotFoundException。调用方不需要知道你用的是MySQL还是Oracle。

已查异常vs未查异常

已查异常（Checked）：可恢复的异常，编译器强制处理。比如文件不存在。

未查异常（Unchecked/Runtime）：程序bug，开发者应该修复而非catch。比如空指针。

原则：如果调用方能恢复，用已查异常。如果调用方无能为力，用未查异常。

异常处理的坏味道

这些模式出现在代码里就是red flag：

  • 返回码代替异常：异常比返回码强大得多，能携带堆栈信息、自动传播
  • 忽略已查异常：catch后空块，等于吞掉错误
  • 捕获Throwable：连Error都catch了，OutOfMemoryError你catch了能干嘛
  • 最外层没有兜底：异常逃逸到框架，用户看到500错误
  • 异常处理只记日志：记了日志但不恢复，系统仍然不可用
  • catch块里写重试：重试逻辑应该抽成独立方法，不该塞在catch里

回头看：如果重来一次

几年后再看那次支付事故，如果重来一次，我会做三件事 differently：

第一，不在catch里返回默认值。默认值的问题是调用方无法区分”正常结果”和”异常兜底”。应该抛出业务异常，让上层决策。

第二，引入熔断机制。下游服务超时不只是单次请求的问题——如果连续超时，说明下游已经不可用。继续调用只会堆积超时请求，拖垮自己的线程池。熔断器在连续失败时直接拒绝请求，保护自身可用性。

第三，事务边界和异常边界对齐。支付接口的事务应该在catch块里回滚，而不是依赖框架的自动回滚——因为你可能在catch里做了部分恢复操作，这些操作本身可能不在事务内。

这几条都是”早该做但当时不知道”的事。经验的意义就在于把”早该知道”变成”现在就知道”。

✅ 总结

  • 异常处理的核心是在错误传播链每一环截断：缺陷→错误→失败。catch了不等于处理了，消除错误状态才是处理
  • 不要返回null，用空对象代替——推这条规范后团队NPE类bug降了70%
  • 异常处理分四级，大多数项目停在”只报告不恢复”。健壮的系统要做到状态恢复甚至行为恢复
  • 分层异常处理：DAO抛基础设施异常，Service包装业务异常，Controller统一兜底。每层只关注自己的职责
  • 熔断机制和事务边界对齐是异常处理的进阶实践——保护自身可用性比处理单个异常更重要
