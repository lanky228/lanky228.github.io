读书笔记 异常处理的设计与重构

发表于 2020-04-05 更新于 2026-08-02 分类于 学习
本文字数： 1.6k 阅读时长 ≈ 1 分钟

💡 异常处理的本质不是”捕获错误”，而是”在错误发生时保持系统可控”。

先搞清楚四个概念

很多人混用”错误”和”异常”，但它们是不同的东西：

  • Fault（缺陷）：代码写错了。比如空指针、逻辑错误。这是根因。
  • Error（错误）：缺陷导致系统进入错误状态。比如HTTP 520，接口内部出错。
  • Failure（失败）：错误状态传播到外部，用户可见的功能丧失。比如页面白屏。
  • Exception（异常）：编程语言中传递上述信息的对象机制。

缺陷→错误→失败，是一条传播链。 异常处理的目标是在传播链的每一环截断它。

最被忽视的原则：不要返回null

返回null是bug的温床。每个调用方都必须记得检查null，但总有人忘。

更好的做法：

  • 返回空字符串""代替null字符串
  • 返回空List代替null集合
  • 使用Null Object模式（返回一个行为正确的空对象）

null逼调用方写防御代码，空对象让调用方无感知。 这不是技巧，是设计哲学。

异常处理的四个等级

等级0：未定义

HTTP 200，return code 0，但功能是否正常不确定。系统没有异常意识，出了问题也不知道。

等级1：错误报告

接口失败时返回具体错误码。至少告诉你”出了什么错”。

规则：

  • 不忽略已查异常
  • 不捕获未查异常（RuntimeException说明代码有bug，不该catch该修）
  • 转抛异常时不记日志（日志在最外层记）
  • 最外层捕获所有异常

等级2：状态恢复

不仅报告错误，还恢复系统状态。

  • 向后恢复：撤销操作、恢复原数据
  • 内存清理、资源释放

等级3：行为恢复

异常时执行备用逻辑，系统继续工作。

  • 诊断、隔离、重新配置
  • 重试
  • 向前恢复：使用备用数据继续处理

等级越高，系统越健壮。但大多数项目停留在等级1——只报告不恢复。

资源管理的陷阱

finally会吞掉异常

如果try块抛出异常A，finally块又抛出异常B，最终抛出的是B——A被吞掉了。

解决方案：try-with-resources（Java 7+）。它自动关闭资源，且不会丢失try块的异常。

try/catch/finally的职责

  • try：资源初始化 + 逻辑处理。只放可能抛异常的代码。
  • catch：异常处理 + 流程重试。捕获你预期会发生的异常。
  • finally：只做资源释放。不要放业务逻辑。

异常设计的原则

命名要表达内容

NotFoundException比Exception12好一万倍。异常名本身就是文档。

低级异常转高级异常

底层抛出的SQLException应该被包装成UserNotFoundException。调用方不需要知道你用的是MySQL还是Oracle。

已查异常vs未查异常

  • 已查异常（Checked）：可恢复的异常，编译器强制处理。比如文件不存在。
  • 未查异常（Unchecked/Runtime）：程序bug，开发者应该修复而非catch。比如空指针。

原则：如果调用方能恢复，用已查异常。如果调用方无能为力，用未查异常。

通道异常

回调函数中，已查异常无法直接抛出（接口不声明）。用未查异常TunnelingException包装已查异常穿过回调边界，在另一端解包。

异常处理的坏味道

这些模式出现在代码里就是red flag：

  • 返回码代替异常：异常比返回码强大得多，能携带堆栈信息、自动传播
  • 忽略已查异常：catch后空块，等于吞掉错误
  • 捕获Throwable：连Error都catch了，OutOfMemoryError你catch了能干嘛？
  • 最外层没有兜底：异常逃逸到框架，用户看到500错误
  • 异常处理只记日志：记了日志但不恢复，系统仍然不可用
  • catch块里写重试：重试逻辑应该抽成独立方法，不该塞在catch里

✅ 总结

  • 异常处理的核心是在错误传播链的每一环截断：缺陷→错误→失败
  • 不要返回null，用空对象代替——逼调用方写防御代码是设计缺陷
  • 异常处理分四级，大多数项目停在”只报告不恢复”
  • 异常命名就是文档，低级异常必须包装成业务异常再抛出
